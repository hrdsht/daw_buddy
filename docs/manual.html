DAW Buddy: what happens between a folder and a row.

A desktop tool that reads music production sessions off disk, pulls the tempo out of proprietary file formats, matches renders to the sessions that made them, and tidies up afterwards. This is how each of those works.

01Two programs, one window

main process · preload bridge · renderer

Electron runs two separate programs that look like one app. The main process is plain Node with full access to your drive. The renderer is a web page with no file access whatsoever. They talk only through a fixed list of functions declared in preload.js.

If you've worked with hardware: the preload script is the pin definition. The untrusted side can only assert the lines you exposed, and nothing else is reachable.

Why it matters more now

Early on the app only read files. It now renames them, rewrites MP3s and replaces duplicates with hard links. Every path arriving from the window is checked against your configured folders before anything is touched — see guard() in main.js.

02One row per session file

the assumption that was wrong, and what replaced it

The app originally assumed one folder equals one project, taking the newest session file in it. Real drives don't work that way.

Olaala bgm idea 3 Project/
  Yogi mom reunion 2.als              08-08-2026
  Yogi babu TEASER INTRO finale.als   08-08-2026
  Yogi mom reunion.als                13-07-2026
  Yogi babu intro opt 3.als           18-06-2026
  Yogi babu intro opt 2 85bpm.als     08-06-2026   ← its own tempo
  …three more

Eight separate pieces of work in one folder, spanning three months. The old model displayed one row and hid seven — which looked like a sorting bug, because work from a given day kept disappearing behind whichever sibling was newest.

Now the session file is the project. Name, date and tempo all come from the file itself. The folder becomes a breadcrumb underneath. Notes were already keyed per session file, so this stopped the display model and the data model fighting each other.

Expected consequence

Project counts go up, often several times over. That isn't inflation — it's what's actually on the drive.

03The scan pipeline

roots → walk → claim → parse → entries

There is no depth setting. The scan goes as deep as your folders go, because asking how deep your own folders are is the app avoiding its job.

What the guards are actually for

The depth ceiling is a backstop, not a policy. What genuinely loops a scan is a junction or symlink pointing at its own parent — a .lnk file can't, because readdir never reports one as a folder. Every folder is resolved to its real path and refused a second visit.

Design rule learned the hard way

Every scanner bug in this project came from an arbitrary limit quietly producing a plausible wrong answer: a depth cap, a twelve-subfolder cap, an eight-thousand-folder budget. If a limit is hit, it must be reported. A truncated result that looks complete is worse than an error.

The FL Studio 26 problem

An .flp is a stream of events. Each starts with an ID byte, and the ID says how much data follows: IDs 0–63 carry one byte, 64–127 two, 128–191 four, 192+ a variable length. Walk it and you find the tempo at event 156, stored as BPM × 1000.

On FL 26 that stopped working. Traced against a real project:

@  46  id= 28  byte   1
@  48  id=172  dword  3221225729     ← 0xC0000101, wrong
@  53  id= 54  byte   70             ← now reading "FL Studio" as events

Event 172 gets read as four bytes and swallows the 0xC0 that begins the next event. Every offset after that is wrong, and the walk marches through 59 KB of misread data without ever reaching the tempo — which sat at byte 128 reading 140 BPM.

Rather than guess which IDs changed size and risk confidently wrong tempos, the walk runs first and a bounded scan of the header region takes over when it comes back empty. Bounded deliberately: scanning the whole file turns up event-66 lookalikes inside pattern data that would report 368 BPM for a 140 BPM track.

Those FL autosave siblings matter twice over. They're newer than the real session, so counting them as sessions meant reading tempo and dates off an autosave — and once excluded, they become the FL backup count that the health bar needed.

05Finding the renders

two searches, two rule sets

The render is rarely inside the project folder:

Suraag/
  Renders/
    Bangalore entry.wav          ← the render
    Bangalore entry 3_2.wav
  Bangalore Entry Bgm/
    Bangalore entry Project/
      Bangalore entry.als        ← the session, two levels down and sideways
The rule underneath a whole class of bugs

Renders and Bounces are skipped when looking for projects and must never be skipped when looking for audio. Two searches with two different jobs need two different rule sets — using one for both was the mistake.

Versions collapse on the way out: Song_7.wav and Song_7.mp3 are one render carrying two formats, not two renders. The bounce watcher uses the same grouping, which is why a render no longer fires two notifications.

06Why it starts fast

what's slow is not what you'd guess

Walking the tree is cheap — readdir and stat cost almost nothing. The expense is opening and un-gzipping every .als to read one number: roughly 50–100 ms per set, so three hundred projects is half a minute of pure decompression, almost none of which changed since last time.

A cached tempo is trusted only when all three still match:

  • mtime — the file hasn't been saved since
  • size — because mtime alone misses two writes in the same second
  • parser version — the code that produced the value hasn't changed
The version stamp is not optional

When the FL parser was fixed, every cached FL tempo became wrong. Without a version stamp the cache would serve those stale values forever — and it would look exactly like the fix had failed. Bumping .flp from 2 to 3 invalidated FL entries only and left Ableton's intact.

Measured on a test tree: first scan 22 ms, second scan 2 ms with nothing re-parsed. Touching one file re-parses exactly one.

Why not do what Everything does

Everything is fast because it never walks folders at all — it reads the NTFS Master File Table directly, a flat table where every file has a fixed-size record pointing at its parent, then keeps current from the USN Change Journal. Chasing a linked list versus reading a contiguous array.

But it needs administrator rights, only works on NTFS, and crucially never opens a file. It knows names, sizes and dates. It could never tell you a BPM. The index isn't the win here; not re-parsing unchanged files is.

07Tools that change files

preview, refuse, undo

Four tools modify things on disk. Each is built so a mistake is recoverable, and each refuses what it doesn't fully understand rather than guessing.

Silence removal

Never writes in place. Reads the folder you point at, writes trimmed copies to the output folder, leaves originals untouched.

  • Dry run first. The preview and the real pass share the same measurement code — if it says 1.99 s, that's what gets removed.
  • Refuses what it can't read — compressed WAV, unknown bit depths, exotic chunk layouts. Skipping a file is an annoyance; corrupting a master is not.
  • Refuses when nothing clears the threshold. Cutting to a 10 ms stub would destroy a file we failed to understand.
  • Rebuilds the header chunk by chunk rather than copying it, so a source that's slightly out of spec doesn't produce an output that is.
  • Leaves a tail. Cutting at the exact sample the audio drops below threshold truncates a decaying waveform and clicks.

Bulk renamer

Nothing moves until you press Apply. Every old → new pair is shown first, collisions are detected before anything is written, and the last run can be undone from a log.

De-duplicator

Collect All means the same sample sits in twenty project folders. This finds them and reclaims the space without deletion.

Why links, not deletion

A hard link is a second name for the same bytes. Both paths keep working, every session still opens, and the drive stores one copy instead of twenty. From the filesystem's point of view nothing was removed — so nothing can break. Deleting a collected sample would mean Ableton asking you to locate it on next open.

ID3 stripper

Pure byte surgery, no library. An MP3 carries an ID3v2 block at the start — sometimes several stacked — and a 128-byte ID3v1 block at the end. Both are cut off and the audio between is written untouched. Verified byte-for-byte: a file with 5 KB of artwork came out with exactly its 20,000 bytes of audio intact.

The size field in an ID3v2 header is syncsafe: each byte uses only its low seven bits, so tag data can never accidentally contain the bit pattern that marks an audio frame. Four bytes carry 28 bits, not 32, which is why the size is assembled with shifts of 21/14/7/0.

Notes are also written beside the project as text files named after the version and the time you last edited them — Nava bharat jodo — 2026-08-13 1634.txt. One per session file, renamed rather than recreated, and .txt is excluded from the bounce watcher so editing a note doesn't fire a render alert.

Renaming the app moved this folder

Electron derives the data folder from the name field in package.json. Changing project-browser to daw-buddy pointed it somewhere empty, which looks exactly like every note vanishing. lib/migrate.js copies the old folder across on first launch — copies, not moves, so the originals remain recoverable by hand.

10Known limits

stated plainly rather than discovered later

  • Key detection is an estimate. On clean material it's right most of the time; on dense mixes with detuned supersaws it may return the relative minor or a fifth away. A confidence figure is shown, and a near-tie usually means the relative key — those share every note.
  • Cubase and Logic tempos aren't read. Both formats are undocumented binaries. Those projects list with everything else working and — for BPM.
  • Off-grid detection needs the tempo in the filename. No BPM in the name means the file is reported as unknown rather than guessed at — a wrong tempo would produce confident nonsense about a fine loop.
  • Windows path length. 260 characters unless long path support is enabled. Deep trees hit the OS limit long before any limit here; the error says so.
  • Cross-drive duplicates are reported, not actioned. Hard links can't span volumes, and deletion isn't offered.
  • Distribution is source, not an installer. Both platforms run npm start. A signed .exe and .dmg need certificates, and a Mac build needs a Mac.
